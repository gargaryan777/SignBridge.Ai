**1. PROJECT OVERVIEW & CORE PROBLEM STATEMENT**
=====================================================================
- Problem scope: People who are deaf or hard-of-hearing in India often face daily communication barriers in schools, healthcare, public services, and casual conversations. Most hearing people do not understand Indian Sign Language (ISL), which forces reliance on interpreters or written notes, slowing communication and reducing independence.
- Project vision: SignBridge provides a real-time, browser-based ISL translation experience that watches hand gestures through a webcam, converts them into text, and speaks them aloud. The goal is to enable direct, fluid, and dignified communication between ISL users and hearing participants.
- What makes it unique: Unlike static, offline translation apps, SignBridge runs inside a live video call, operates hands-free, and delivers immediate voice output with low latency. It also includes accessibility-first features like quick phrases, SOS alerts, and chat dictation, making it a complete communication platform rather than a single-use translator.

**2. END-TO-END ARCHITECTURE & DATA FLOW**
=====================================================================
Step 1 (Frontend/Capture)
- The main app UI is served from the Node.js server and rendered by HTML/JS in the browser.
- The camera stream is initialized via `navigator.mediaDevices.getUserMedia` with video and audio enabled.
- MediaPipe Hands is loaded from a CDN and runs directly in the browser. The app captures frames at 640x480 and forwards them to the MediaPipe pipeline.
- The UI overlays live landmarks on the video, shows prediction confidence, and provides controls for mic, camera, and ML toggles.
- Prediction requests are throttled to roughly one inference every 150 ms to keep the UI smooth and latency stable.

Step 2 (Feature Extraction/Tracking)
- MediaPipe Hands detects up to two hands per frame.
- For each detected hand, 21 landmarks are produced. Each landmark provides 3 values: x, y, z.
- The app builds a flat feature vector of length 126 (2 hands * 21 landmarks * 3 coordinates). If only one hand is visible, the remaining slots are padded with zeros.
- The app sorts hands by their x-position to ensure a consistent left-to-right feature order.

Step 3 (ML Classification / Processing)
- The browser sends the 126-value landmark vector to the backend `/predict` endpoint.
- The Node.js server proxies this request to the Python Flask service to isolate the ML stack.
- The Python service normalizes landmarks by shifting all points to be wrist-relative and scaling by maximum wrist distance, then applies a StandardScaler.
- The trained RandomForest model outputs class probabilities and the most likely sign.
- If confidence is below 0.40, the system returns "Uncertain" to avoid incorrect output.
- On the frontend, predictions are appended to the live sentence only if confidence exceeds 0.60 and the predicted token differs from the previous one.

Step 4 (LLM/Contextual Smoothing)
- No LLM or NLP smoothing layer is implemented in the current codebase.
- Sentence construction uses a deterministic concatenation strategy based on confidence thresholds and word change detection.
- The design leaves room for a future NLP layer without changing the current pipeline.

Step 5 (Output Layer)
- The translated text appears in a live transcript panel and can be copied or cleared.
- For audio, the system first tries ElevenLabs TTS through the Flask `/speak` endpoint. If no API key is available, it falls back to browser SpeechSynthesis voices.
- The TTS panel allows typed text to be spoken and optionally shared into the room chat.

**4. CORE FEATURES & IMPLEMENTATION DETAILS**
=====================================================================
- Real-time video/gesture processing
  - MediaPipe runs in the browser, extracting 21 landmarks per hand in real time.
  - The prediction loop is throttled to avoid UI stutter and excessive backend calls.
  - Landmark features are normalized for scale and position stability before classification.
- Multi-modal output (Text + Audio)
  - Live translation text is appended based on confidence and word change checks.
  - ElevenLabs TTS is used when available; browser speech synthesis is a guaranteed fallback.
  - A dedicated TTS panel allows typed messages to be spoken and shared into the session.
- UI/UX highlights
  - Live confidence meter, translation overlay, and gesture counters give immediate feedback.
  - WebRTC video calling is embedded with a room code flow for peer discovery.
  - Accessibility tools include quick phrases, emotion reactions, and SOS alerts with audio.
- Low-latency optimizations
  - Prediction is throttled to 150 ms intervals.
  - Confidence gating avoids frequent incorrect outputs.
  - Wrist-relative normalization and scale normalization stabilize input features for more consistent inference.

**6. EXPECTED PRESENTATION Q&A (VIVA CHEAT SHEET)**
=====================================================================
1) Q: How does your model avoid incorrect translations in live use?
   A: The backend returns "Uncertain" below 0.40 confidence, and the UI only appends words above 0.60 confidence. This two-stage gating prevents noisy predictions from being spoken or added to the transcript.

2) Q: Why did you use wrist-relative normalization in the features?
   A: Wrist-relative coordinates remove absolute position and scaling effects so the model learns hand shape rather than where the hand is on screen. This improves robustness across different users and camera placements.

3) Q: Why RandomForest instead of a deep learning model?
   A: RandomForest provides fast inference with strong accuracy for landmark-based features and requires less data to train. It is a strong baseline for real-time systems with low latency constraints.

4) Q: How is real-time video calling integrated with the translator?
   A: WebRTC handles the peer-to-peer video stream, while Socket.IO provides signaling and room coordination. The translation runs locally in the browser and sends only landmark vectors to the ML backend.

5) Q: Is there any LLM-based sentence correction or grammar layer?
   A: No. The current implementation uses deterministic concatenation and confidence thresholds. This is intentional for low latency and transparency, and the architecture allows a future NLP layer without breaking the pipeline.
